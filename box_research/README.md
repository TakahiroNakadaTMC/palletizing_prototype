## 1. 概要

本レポートは、パレタイズアルゴリズム試作プロジェクトにおいて対象とする**工業用TP規格コンテナ**および**代表的非TP規格箱（折りたたみコンテナ・一般通い箱・番重）**の寸法・嵌合（かんごう）深さ・リブ仕様を調査・整理した成果物です。

箱・蓋のデータベースは [box_db.json](box_db.json) と [lid_db.json](lid_db.json)、
パレットのデータベースは [pallet_db.json](pallet_db.json) に格納されています。

### 品番DB移行の事前確認（第1段階・未適用）

第1段階の確認後、第2段階の新DB登録まで実装済みです。
以下の事前確認ツールは引き続き元データを変更せず利用できます。

[preview_migration.py](preview_migration.py) は、[入力CSV](box_list.csv)、
現在の箱・蓋DB、採否にかかわらず全ケースを読み取り、移行予定の確認資料を作ります。
DB、CSV原本、ケース、採用状態、計算結果、ビューアは変更しません。
この段階では新DBの適用やパレタイズ計算は行いません。

```powershell
python .\box_research\preview_migration.py --output-dir .\migration-review-phase1
python -m unittest box_research.preview_migration_test box_research.database_validation_test
```

出力先は、まだ存在しない確認資料専用フォルダを指定してください。
既存フォルダへの上書きは拒否します。再実行時は別の出力先を指定します。

| 出力 | 確認する内容 |
| --- | --- |
| `preview.json` | 全体件数、共通モデル・蓋の仕様案、元ファイルのSHA-256、適用していないこと |
| `parts.csv` | 品番、仕入先、箱名称、共通モデル名、固定蓋、元CSVの行番号 |
| `cases.csv` | 各ケースの箱行、維持する数量、選択品番、候補一覧、選択方法 |
| `changes.csv` | 文字の統一、蓋の略称解決、明示された訂正などの変更予定 |
| `issues.csv` | 完全重複の統合、第一候補の仮選択、移行を止める問題 |

SHA-256は「入力内容が変わっていないかを確認するための照合値」です。
入力が調査中に変わった場合は保存前にエラーにします。
終了コードは0が調査完了、2が確認資料は生成したものの移行を止める問題あり、
1が読込み・出力等の実行失敗です。0でも実装やデータ移行の承認を意味しません。

CSV列の `part_number` / `id` は品番、`box_name` は箱名称、
`box_model_id` は共通箱モデル名、`lid_id` は固定蓋です。
`unique` は候補1件、`first_candidate` は複数候補からCSV順の最初を仮選択、
`unmatched` は対応なしを意味します。`blocker` は移行を止める問題、
`review` は確認対象、`info` は処理内容のお知らせです。
CSVをExcel等で取り込むときは、品番列を「文字列」に指定してください。
CSV自体は品番を文字列として出力しますが、表計算ソフトの自動変換には注意が必要です。

適用予定のルールは次のとおりです。

- 品番を文字列として扱い、完全に同じCSV行だけを統合する。
- 型式の空白は無蓋、TP330等は対応するフタIDへ読み替える。
- 指定済みの3品番は130902501000→TP34蓋、153702502000→TP340フタ、
  155202501000→無蓋とする。その他の互換性は現在のDBを正とする。
- NP22C・NPP24はサンボックス#22H、SPZ36404・SPZ36406はTP364へ対応付ける。
  その他は寸法一致だけで統合せず、現在の箱名称をモデル名として残す。
- NEUAD9とNS80858は、ユーザー指定の寸法・非TP区分・嵌合深さ・リブ厚を仕様案に追加する。
- クゼーはグゼー、NITTANはニッタンへ統一する。
- 半角カタカナ、全角英数字、全角の＃・－・空白を統一し、前後の空白を除く。
  英字の大小、内部の連続空白、その他の記号は同一視しない。
  制御文字・不可視文字を含むIDはエラーとし、変換後のID衝突は自動統合しない。
- サンボックス＃22Bの蓋IDはサンボックス#22Bフタへ名称訂正する。
- ケースの仕入先・箱名称・蓋が一致する有効な品番からCSV順の第一候補を選ぶ。
  数量は維持し、候補がない場合は未選択のまま問題として報告する。
- TP331等の上載せ支持点数を明示し、後のモデル名変更で条件が失われないようにする。

**確認フェーズ:** 出力された品番・蓋・モデル対応と、ケースの第一候補をユーザーが確認します。
問題の解消と第2段階への明示的な合意があるまで、DBやケースへ適用しません。
このツールに適用用のオプションはありません。

第1段階の承認済み対応案から、次の新DBを [catalog/](catalog/) に登録しました。

| ファイル | 内容 |
| --- | --- |
| [box_type_db.json](catalog/box_type_db.json) | 362品番。品番・仕入先・箱名称・共通箱モデル名・固定蓋 |
| [box_model_db.json](catalog/box_model_db.json) | 81箱モデル。共通モデル名自体がIDで、寸法・嵌合深さ・互換蓋・支持点数を保持 |
| [lid_db.json](catalog/lid_db.json) | 24種類の蓋。文字統一と名称訂正後のID、既存仕様 |
| [migration.json](catalog/migration.json) | 元データの照合値、全150ケース・200行の品番対応案、旧名称との対応、名称変更履歴 |

第2段階での `phase` は `phase2_pending_activation`（登録済み・切替前）です。
第3段階のケース作成時は `phase3_pending_algorithm`（画面対応済み・計算未対応）です。
第4段階は `phase4_pending_validation`、現在は `phase5_ready`（品番方式の計算・独立検証・結果表示対応済み）です。
モデル数は旧箱81件から指定された2組を各1件へまとめ、追加箱2件を加えた81件です。
NEUAD9は540×365×70 mm、嵌合深さ5 mm、リブ厚15 mm、
NS80858は1400×1000×800 mm、嵌合深さ10 mm、リブ厚15 mmで、両方とも非TPです。

**段階移行のための配置変更:** 当初案のように既存の箱DBをすぐモデルDBへ置き換えると、
未対応のCLI・Supervisor・画面が動かなくなります。そのため新DBを専用フォルダへ分離しました。
既存の [box_db.json](box_db.json)、[lid_db.json](lid_db.json)、ケース、採用状態、
パレットDB、計算結果は変更していません。
新しい蓋DBは第3段階の専用画面から編集できます。
第4段階の品番方式CLIは新DBを参照し、従来画面と旧方式の計算は旧DBを参照します。
旧DB等を変更すると新DBとの食い違いを検出して処理を止めます。自動的に片方へ寄せません。
新方式は計算・独立検証・3D表示とも明示指定で実行し、旧方式のデータと分離して使います。

[catalog_store.py](catalog_store.py) が登録・検証・名称変更・保存を担当し、
保存前の検証と文字統一は [database_validation.py](database_validation.py) を使います。
未登録の参照、非互換の蓋、重複ID、空のID、制御文字、不正な数値
（真偽値、文字列、負数、NaN、無限大など）、L<W、嵌合深さ≧箱高は拒否します。
嵌合深さ・リブ厚は0を許容し、無蓋の寸法はすべて0とします。
支持点数4/5は名前に依存せず明示して保存します。
新方式ケースの仕入先と品番の一致、数量1〜500の整数、固定蓋の不正な上書きも
専用の検証関数で確認します。既存ケース保存APIにはまだ接続していません。

```powershell
# 保存済み新DBと元データの整合性を確認（変更しない）
python .\box_research\catalog_store.py check

# 名前変更の事前確認（変更しない）
python .\box_research\catalog_store.py preview-rename "サンボックス#22H" "変更後のモデル名"

# 影響する品番・ケースを確認してから実行
# <確認番号>には直前の結果の confirmation の値を入れる
python .\box_research\catalog_store.py rename "サンボックス#22H" "変更後のモデル名" --confirm "<確認番号>"
```

名前変更はモデルのキーと `id`、紐付く全品番、旧箱名称からの対応、過去のモデル名からの対応を
まとめて更新します。既存モデルや過去の名前との重複は拒否します。
ケースは品番対応案だけを参照するため、ケース原本を書き換える必要はありません。
確認後にDBが変われば確認番号が無効になり、再確認が必要です。
第2段階では上記コマンドだけでしたが、第3段階で名前変更の画面も追加しました。

保存中は他の保存をロックで拒否し、全ファイルを準備してから置き換えます。
途中で置換に失敗した場合は元に戻し、復元にも失敗した場合は復旧用コピーの場所をエラー表示します。
電源断等を含む完全なトランザクションを保証するものではありません。
強制終了で `.save.lock` が残った場合は、保存処理が終了していることを確認するまで削除しないでください。
DBファイルの直接編集ではこれらの保存保護を通らないため、通常は上記の処理を使ってください。

### DB・品番ケース編集画面（第3段階・計算への切替前）

```powershell
python .\box_research\serve_viewer.py
# またはケース用サーバー
python .\test_programmer\serve_testcase_viewer.py
```

起動時に開く従来画面の上部リンクから、新画面へ移動します。
両方のサーバーで同じ新画面と保存APIを使えます。
ポートは起動時の表示を確認してください。既定ポートの場合は次のURLです。

- DB編集: `http://localhost:8081/catalog_viewer.html`
- 品番ケース編集: `http://localhost:8083/catalog_cases.html`
- 片方だけ起動した場合も、同じポート上の両ページを利用できます。
- 新画面は外部CDN・追加JavaScriptライブラリ不要です。HTMLを直接開かずサーバーを使ってください。

DB画面には4つのタブがあります。

| タブ | 操作 |
| --- | --- |
| 品番・箱種DB | 仕入先・箱名称・モデル・固定蓋の追加、編集、削除。モデルに合う蓋と無蓋から選択 |
| 箱モデルDB | 寸法・嵌合深さ・リブ厚・互換蓋・支持点数の追加と編集。名前変更は関連品番・蓋・ケースを確認して別操作 |
| 蓋DB | 寸法・高さ増加・嵌め方等の追加、編集、削除。既存IDは編集不可 |
| パレットDB | 型番・本体L/W/H・仕入先の参照。編集は従来DB画面のパレットDBタブを引き続き使用 |

品番と既存蓋IDは、編集時には変更できません。使用中の品番・モデル・蓋の削除は拒否します。
旧箱名称から参照されているモデルも保護します。新しい名前への変更はモデルの「名前変更」を使います。
未保存の編集がある間は名前変更できません。まず保存または再読み込みしてください。

**保存の流れ:** 「追加」または「編集」→入力→「入力を確定」→画面上部の
「品番方式の変更をまとめて保存」です。タブ切替では編集中のデータを保持します。
検索は表示のみであり、保存対象を絞りません。再読み込みは未保存内容を確認してから破棄します。
エラーは画面上部に表示し、保存失敗時は未保存データを保持します。
別画面で更新済みなら上書きせずエラーにします。画面を離れる際にも未保存の警告を要求します。

品番ケースは [catalog/test_cases.json](catalog/test_cases.json) にまとめて保存します。
元ケース150件・200箱行の数量、説明、パレット条件、採用状態を引き継いだ
**別コピー**です。`test_cases` がケース一覧、`approval_state` が準備用採用状態です。
箱行は `part_number` と `count` だけを持ち、箱と蓋は品番DBから決まります。
第1段階で複数候補だった80行はCSV順の第一候補を引き継ぎ、
編集ダイアログで移行時の候補を確認して変更できます。
元の割当て履歴は移行情報に残し、現在の編集内容とは分けて扱います。

- ケースは仕入先→品番→数量の順で選びます。品番・箱名称で候補を検索できます。
- 箱名称・共通モデル名・固定蓋を自動表示し、ケース内で蓋を変更する操作はありません。
- パレットは仕入先に対応する仕様と全仕入先共通の標準パレットだけを選べます。
  本体寸法は選択肢に表示し、ケースには荷山上限3項目を保存します。
- 既存ケースIDは変更不可。新規ケースは不採用で作成します。
- ケースの追加・編集・削除、個別採用・一括採用／解除は準備用データだけに反映します。
- 仕入先を変更すると品番行をクリアするため、先に確認します。
- 品番・モデル・蓋の保存時も、準備用ケースとの整合性をサーバーで再検証します。
  従来パレット編集側も準備用ケースの参照を確認し、使用中仕様の削除や不整合な変更を拒否します。

### パレットDB（2026-11-05）

- 箱・蓋と同じ統合ビューアに「パレットDB」タブを追加しました。
  `python box_research/serve_viewer.py` で起動し、`http://localhost:8081/#pallets` を開きます。
- `pallet_db.json` はパレット仕様を `pallets` オブジェクトに保持します。
  各レコードの `id` はキーと一致し、`model`、`length`、`width`、`height`、
  `suppliers`（その仕様を使用する仕入先名の配列）を持ちます。
- 同じ型番・同じ寸法のパレットは共通仕様として1件にし、仕入先を複数紐付けます。
  同じ型番でも寸法が異なる場合は別仕様として登録します。
- DBビューアで型番、仕入先、L/W/Hを追加・編集できます。仕入先は「、」またはカンマで区切ります。
  テストケースから参照されている仕様は削除できません。
- 保存時はケースのパレットIDと仕入先の対応を確認します。本体寸法はパレットDBを正とし、
  ケース内のL/W/Hとの一致は要求しません。現行ケースは本体寸法を重複保存しないためです。
  旧ケースに寸法が残っていても比較せず、ケース自体を書き換えることはありません。
- 「標準パレット（型番未指定）」1200×1000×130 mm は全仕入先共通の固定候補です。DBタブには表示しますが編集・削除できません。
- テストケース作成画面では仕入先を先に選び、その仕入先の型番を寸法付きで選択します。
  パレット本体L/W/Hは型番選択肢に表示します。ケースJSONには `pallet_id` を保存し、L/W/Hは実行時にDBから解決します。作成画面に本体寸法入力欄はありません。

## 2. TP規格コンテナの体系とモジュール仕様

### 2.1 TP規格とは

自動車産業・製造業物流において標準化されたプラスチックコンテナ規格（Toyota Plastic Box / JIS準拠）です。
**基準モジュール寸法（間口 335 mm × 奥行 335 mm）** を単位とし、倍数・分数関係にある異なる型番同士でも**底面のTP格子リブ構造により相互嵌合（スタッキング）が可能**です。

### 2.2 TP規格の平面モジュール関係

```text
 ┌───────────────┬───────────────┐
 │   TP-330系    │   TP-330系    │
 │ (335 x 335)   │ (335 x 335)   │  ──► 合計: 670 x 335 mm (TP-360系と完全一致)
 ├───────────────┴───────────────┤
 │           TP-360系            │
 │         (670 x 335)           │
 └───────────────────────────────┘

 ┌───────────────────────────────┐
 │           TP-360系            │
 │         (670 x 335)           │
 ├───────────────────────────────┤  ──► 合計: 670 x 502.5 mm (TP-460系と完全一致)
 │   TP-130系    │   TP-130系    │
 │ (335 x 167.5) │ (335 x 167.5) │
 └───────────────┴───────────────┘
```

TP規格の平面寸法は、実寸では167.5 mmを基本ピッチとします。
従来の168 mm、503 mm、838 mm等はカタログ上の四捨五入表記です。
DBおよび計算では、それぞれ167.5 mm、502.5 mm、837.5 mmを使用します。

| シリーズ | 外寸長さ L (mm) | 外寸幅 W (mm) | モジュール比率 | 嵌合互換性 |
| :--- | :---: | :---: | :---: | :--- |
| **TP-110系** | 167.5 | 167.5 | $0.5 \times 0.5$ | 4個で TP-330系 1個と同フットプリント |
| **TP-130系** | 335 | 167.5 | $1.0 \times 0.5$ | 2個で TP-330系 1個と同フットプリント |
| **TP-330系** | 335 | 335 | $1.0 \times 1.0$ | **基準モジュール** |
| **TP-340系** | 502.5 | 335 | $1.5 \times 1.0$ | 2個で1005x335 mm (3.0x1.0) または340系2列(502.5x670 mm)のフットプリントを構成 |
| **TP-360系** | 670 | 335 | $2.0 \times 1.0$ | TP-330系 2個の上/下に嵌合段積み可能 |
| **TP-460系** | 670 | 502.5 | $2.0 \times 1.5$ | TP-360系(2x1) + TP-130系(2x0.5) や TP-340系(1.5x1) 2個とモジュール整合 |
| **TP-480系** | 837.5 | 502.5 | $2.5 \times 1.5$ | 特大モジュール |
| **TP-490系** | 1005 | 502.5 | $3.0 \times 1.5$ | 1200x1000 パレット向けの大型モジュール |

### 2.3 高さ体系と嵌合深さ (fitting_depth)

TP規格の高さは規格化されており、異なる高さの箱を組み合わせても段積み全体の高さを揃えやすくなっています。

- **高さの基準寸法**: 型高さを $n$ とすると、外寸高さは $H = 92.5n + 10$ mm。
- **代表的な外寸高さ（実寸）**:
  - **1型 (浅型)**: 102.5 mm（カタログ表記: 103 mm）
  - **1.5型 (中浅型)**: 148.75 mm（カタログ表記: 149 mm）
  - **2型 (標準型)**: 195 mm
  - **2.5型**: 241.25 mm（カタログ表記: 241 mm）
  - **3型 (深型)**: 287.5 mm（カタログ表記: 288 mm）
  - **4型**: 380 mm
- **嵌合深さ (`fitting_depth`)**:
  - TP規格箱全系統: **10.0 mm**
- **段積み総高さの計算式**:
  $$H_{total}(N) = H_{bottom} + \sum_{k=2}^N (H_k - fitting\_depth_k)$$
  - `fitting_depth` は上段箱の嵌合沈み込み量です。
    `fitting_depth=10 mm` の場合、同じ型高さの箱を1段追加したときの高さ増分は
    $H-10=92.5n$ mmです。

### 2.4 上縁幅 (`rib_thickness`) の定義

**箱を上から見たときの、外側の縁から開口部側の縁までの幅**を入力します。樹脂単板の肉厚や、底面で測った片側側壁の厚みを表す項目ではありません。

同じ上面位置で測った外寸・開口寸法が左右対称であれば、その差の半分が目安になります。ただし、テーパーや内寸の測定位置によって一致しないため、有効内寸・底面内寸からの自動計算は行いません。

既存DBの値はそのまま保持します。過去に内寸差から推定された値については、この定義による実測済み値であることを保証するものではありません。更新時は上縁の測定位置を確認してください。

## 3. パレット (1200x1000) への適合性考察

1. **TP-340系 (502.5 × 335 mm)**:
   - 長辺 1200mm に対して $502.5 \times 2 = 1005\text{ mm}$、
     または $335 \times 3 = 1005\text{ mm}$、
     $335 \times 4 = 1340\text{ mm}$（1360mm未満許容枠内！）。
   - 短辺 1000mm に対して $335 \times 3 = 1005\text{ mm}$ や
     $502.5 \times 2 = 1005\text{ mm}$ は、いずれも許容スパン $1100\text{ mm}$ 未満。
     安定性の下限 $800\text{ mm}$ も満たす配置を選定する。
2. **TP-360系 (670 × 335 mm) & TP-460系 (670 × 502.5 mm)**:
   - 長辺 1200mm に対して $670 \times 2 = 1340\text{ mm}$（**長辺1360mm未満の許容枠を最大限に活かしたジャストフィット配置**が可能！）。
   - 短辺 1000mm に対して $502.5 \times 2 = 1005\text{ mm}$、
     または $502.5 + 335 = 837.5\text{ mm}$ は、
     いずれも $800\text{ mm} \le Y_{span} < 1100\text{ mm}$ を満たす。

## 4. 蓋データベース仕様（Phase 2 新規追加）

### 4.1 蓋DB の位置づけ

- **ファイル**: `box_research/lid_db.json`
- **目的**: パレタイズ対象箱に対応する蓋（フタ）の仕様を一元管理
- **用途**:
  - テストケース生成時の蓋選択肢の提供
  - パレタイズ結果への蓋情報付加（将来拡張）
  - UI上での箱-蓋関連性の可視化

### 4.2 蓋データ項目

各蓋について以下を管理：

| フィールド | 型 | 説明 |
| ----------- | ----- | ------ |
| `id` | string | 蓋識別子（例: `"LID-001"`） |
| `name` | string | 蓋の名称（例: `"TP-330系対応クリア蓋"`） |
| `type` | string | 蓋の規格タイプ（例: `"TP"`, `"OTHER"`） |
| `length` | float | 蓋の外寸長手方向 L [mm] |
| `width` | float | 蓋の外寸短手方向 W [mm] |
| `thickness` | float | 蓋装着時の高さ増加量 [mm]。蓋単体の全高や天板の肉厚ではない |
| `fit_type` | string | 蓋の嵌め方：`"外嵌め"` \| `"内嵌め"` \| `"なし"` |
| `color` | string（任意） | 色名。未設定は空文字、旧データの項目省略も可 |
| `description` | string | 対応規格や特徴の説明 |

**fit_type の定義**:

- `"外嵌め"`: 箱外側面と蓋で位置決め（標準方式、9個の蓋）
- `"内嵌め"`: 箱内壁面と蓋で位置決め
- `"なし"`: 蓋を使用しない場合（universal option、LID-010）

### 4.3 箱と蓋の互換性管理

Phase 2 で箱DB（`box_db.json`）を拡張し、各箱に `compatible_lids` フィールドを追加：

- **フィールド**: `compatible_lids` (array of string)
- **内容**: 当該箱に対応する蓋IDリスト
- **例**:

  ```json
  {
    "id": "TP-331",
    "name": "TP-331コンテナ",
    "compatible_lids": ["LID-001", "LID-002"]
  }
  ```

- **全体方針**: `compatible_lids` には箱に対応する実蓋のみを登録する。蓋DBの `type: "NONE"` は全箱共通の選択肢として扱い、箱ごとの互換リストには登録しない。

### 4.5 技術的ハイライト

- **REST API**: `serve_viewer.py` に蓋DB用エンドポイントを実装
  - `GET /api/lids` — 蓋DB全体を取得
  - `POST /api/lids/save_all` — 蓋DB全体を保存
  - `GET /api/box_references`・`GET /api/lid_references` — 箱ID・蓋IDごとの参照テストケース名を取得
  - `POST /api/databases/save` — 統合画面から箱・蓋を保存。`{"boxes": {...}}`、`{"lids": {...}}`、または両方を指定。互換蓋参照・テストケース参照を検証し、全ファイルを一時ファイルへ書き出してから置換します。置換失敗時は既に置換したファイルを元に戻し、エラーを返します。OS停止・プロセス強制終了に対する複数ファイルの完全なトランザクション保証ではありません。復元にも失敗した場合は、エラーに復旧用ファイルの場所を表示します。
- **UI**: HTML5 + Tailwind CSS で蓋管理画面を実装
  - 蓋統計（総数、外嵌め数、内嵌め数）を表示
  - 蓋の追加・編集・削除をモーダルフォームで実行
  - fit_type をドロップダウンで選択
- **データ永続化**: UTF-8 JSON ファイルとして直接保存（DB エンジン不要）

### 4.6 蓋の色情報（任意）

- `color` は「黒」「青」「透明」などを記録する任意の文字列項目。未設定は空文字 `""` とする。
- 蓋一覧の「色」列と追加・編集フォームに対応。項目のない旧データも未設定として扱う。
- 保存時に色情報を保持する。色名から既存データの色を推測して設定しない。
- 現時点ではパレタイズ計算・制約検証・3Dビューアの描画色には使用しない。
